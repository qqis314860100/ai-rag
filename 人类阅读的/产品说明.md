# RAG 知识库平台 — 产品规格与实施计划

> 版本：v2.0 | 日期：2026-05-22 | 状态：第一阶段基本完成，持续迭代

---

## 1. 项目背景

### 1.1 当前状态

公司现有 **EP (Rosefinch)** 平台，Java 后端 + React 前端，面向宁德时代电池 MP 产线 T_X 模型，提供图纸/模型（.x_t）、技术文档（PDF/Word）、图片等文件的传统管理能力（上传、检索、预览）。搜索为关键词+筛选项匹配，不支持内容级检索。

### 1.2 目标

构建 **enterprise-rag-kb** — 一个可独立部署的 RAG 知识库平台，引入 AI 语义搜索与智能问答能力。让产线工程师通过自然语言快速检索文件内容、获取技术知识。设计上保持"可嵌入"能力，后续可集成到 EP 或其他系统中。

### 1.3 与 EP 系统的关系

| 维度 | EP 系统 | enterprise-rag-kb |
|------|---------|-------------------|
| 定位 | 文件管理平台 | AI 知识库引擎 |
| 后端 | Java (Rosefinch) | Node.js/Express |
| 数据库 | PostgreSQL | SQLite（可迁 PG） |
| 搜索 | 关键词+筛选 | 关键词 + **AI语义搜索** |
| 文件处理 | 存储+元数据 | 存储+元数据 + **内容解析+向量化** |
| 前端 | Umi4+React | React 19+Vite（可独立部署或嵌入EP） |
| AI能力 | 无 | **RAG全链路（解析→检索→生成）** |

## 3. 当前系统现状

### 3.1 已完成功能清单

**前端 (web)**
- `/chat` AI 对话页：会话列表、多轮对话、流式打字机效果、引用来源面板、文档预览、追问建议、重试/编辑/停止
- `/documents` 文档管理页：上传（拖拽）、分类筛选、索引状态、安全等级、版本、chunk 评论
- `/search` 搜索页：传统关键词搜索
- `/settings` 设置页：RAG 参数在线调整（top_k/temperature/embedding_model 等）、RAG 健康检查
- `/admin` 管理页：用户管理、角色管理、审计日志
- `/login` 登录页、AuthContext 全局认证

**API 网关 (api)**
- 认证体系：JWT 签发/验证/刷新、7 种角色、细粒度权限中间件
- 文件管理：multer 上传（白名单校验、UUID 防穿越）、分类/工位/版本/安全等级
- 对话管理：会话 CRUD、消息持久化、SSE 流式代理、来源引用 N:M 关联
- 搜索：传统关键词 LIKE 搜索 + AI 语义搜索转发
- 反馈：点赞/点踩、原因标注、处理状态流转
- 审计：操作日志全量记录（操作人/IP/UA/RequestID）
- 统计：仪表盘概览数据
- RAG Client：HTTP 调用封装、指数退避重试、超时控制

**RAG 引擎 (rag)**
- 文档解析管道：PDF (PyMuPDF) / Word (python-docx) / Markdown / TXT
- 文本清洗 + 分块（500 tokens/块，50 tokens 重叠）
- Embedding：BAAI/bge-small-zh-v1.5（384 维），fallback 纯 Python 模式
- 向量检索：ChromaDB 持久化，安全等级过滤
- LLM 调用：DeepSeek API（OpenAI 兼容协议），流式 SSE
- Prompt 模板：System Prompt + Context Injection + History + 引用标注指令
- 调试端点：含 Prompt 预览、检索耗时、分块详情

### 3.2 已预留但未启用的能力

| 能力 | 当前状态 | 启用成本 |
|------|----------|----------|
| .x_t 文件解析 | 代码已标记，Parser 未注册 | 注册 Parser + 测试 |
| Agent 体系 | 表结构已建（agents/agent_tools/agent_memories） | CRUD 路由 + 前端 UI |
| Agent 记忆 | 表结构已建 | 记忆读写逻辑 |

| OCR 图片识别 | Parser 未引入 | 加 PaddleOCR/Tesseract |

### 3.3 技术债务

| 项 | 现状 | 建议 |
|----|------|------|
| 数据库 | SQLite 单文件 | 数据量 > 10万条时迁 PostgreSQL |

## 5. 关键流程

### 5.1 文档上传 → 知识入库

```
用户上传文件 → multer 存到 data/uploads/（UUID 文件名）
             → SQLite 写 documents 表（index_status=pending）
             → 异步: POST /rag/documents/ingest { document_id, file_path, metadata }
                      │
                      ▼
                Python RAG Pipeline:
                  1. ParserRegistry 识别文件类型
                  2. 解析提取文本 + 表格
                  3. 文本清洗（去噪/标准化）
                  4. 分块（500 tokens/块，50 tokens 重叠）
                  5. 调用 Embedding 模型转 384 维向量
                  6. delete_by_document → upsert 到 ChromaDB
                      │
                      ▼
                回调更新 SQLite: index_status=ready/failed, chunk_count
```

### 5.2 AI 搜索/对话（流式 SSE）

```
用户输入自然语言问题
       │
       ▼
前端 POST /api/chat { session_id, message, top_k }
       │
       ▼
Express API:
  - 验证 JWT Token，提取 user_id + role
  - 确定可见 security_levels（internal / confidential / restricted）
  - 转发 POST /rag/chat/stream { query, top_k, allowed_security_levels, history }
       │
       ▼
Python RAG:
  1. embed_query(query) → 384 维向量
  2. ChromaDB 向量检索 Top-K（按 security_level 过滤）
  3. build_messages(query, chunks, history, max_context_chars)
  4. 调用 DeepSeek API chat/completions (stream=true)
       │
       ▼
SSE 事件流:
  data: {"type":"meta","retrieval_ms":342,"hit_count":5}
  data: {"type":"chunk","content":"根据知识库中的"}
  data: {"type":"chunk","content":"《T_X 产线工艺规范》..."}
  ...
  data: {"type":"done","sources":[{document_id,title,section,page,score,snippet}],
         "confidence":0.87,"followups":["焊接时间参数？","温度超标处理？"]}
       │
       ▼
前端渲染:
  - useStreamChat 打字机效果（~120 字符/秒）
  - 引用卡片可点击跳转文档详情
  - 追问建议按钮
  - 回答反馈（点赞/点踩）
```

### 5.3 传统关键词搜索（保留并存）

```
用户输入关键词 → GET /api/search?keyword=xxx&category=xxx
              → Express 查 SQLite documents 表 LIKE 匹配
              → 返回文件列表（毫秒级，不经过 RAG）
```

两种搜索模式可在 `/search` 页面通过 Toggle 一键切换。

## 6. 数据层

### 6.1 数据库表结构

```
users               — 用户（name/email/password_hash/role/status）
roles               — 角色定义（7种预置角色）
role_permissions    — 角色-权限关联
documents           — 文档元数据（标题/分类/工艺/工位/版本/安全等级/索引状态/文件路径）
document_versions   — 版本历史（document_id/version/file_path）
document_jobs       — 异步任务追踪（document_id/job_type/status/progress）
chat_sessions       — 对话会话（user_id/title/pinned）
chat_messages       — 对话消息（session_id/role/content/sources_json/latency_ms/token_count）
message_sources     — N:M 引用来源（message_id/chunk_id/document_id/score/snippet）
feedback            — 回答反馈（message_id/user_id/rating/reason/status/resolution）
browse_history      — 浏览记录
doc_comments        — 文档 chunk 级评论（支持嵌套回复 parent_id）
audit_logs          — 审计日志（operator/action/resource/ip/request_id）
settings            — 系统设置（key-value, rag参数在此）
agents              — Agent 定义（name/system_prompt/model/temperature/tools_json）
agent_tools         — Agent-工具绑定
agent_memories      — Agent 长期记忆（user_id/agent_id/key/value/importance）
```

### 6.2 文档分块策略

| 文件类型 | 分块方式 | 块大小 | 重叠 | 备注 |
|---------|---------|--------|------|------|
| PDF（文本型） | 按章节+段落 | 500 tokens | 50 tokens | 保留章节路径 |
| Word | 按段落 | 500 tokens | 50 tokens | 保留标题层级 |
| Markdown | 按标题+段落 | 500 tokens | 50 tokens | 保留标题层级 |
| TXT | 按段落 | 500 tokens | 50 tokens | 无结构信息 |
| .x_t | **仅文件头+零件编号** | — | — | 第一阶段不做全文切片 |
| 图片 | OCR 后整段 | — | — | 待引入 OCR |

## 8. 技术栈

| 层 | 技术 | 选型理由 |
|----|------|----------|
| 前端框架 | React 19 + TypeScript | 生态成熟，与 EP 前端技术栈对齐 |
| 构建 | Vite 6 | 开发体验好，HMR 快 |

| 业务数据库 | SQLite (better-sqlite3) | 零运维，单机够用；可迁 PG |

| Embedding | BAAI/bge-small-zh-v1.5 | 中英双语，384 维，轻量（~133MB） |
| LLM | DeepSeek API (deepseek-chat) | OpenAI 兼容协议，可无缝切换公司模型 |
| 文档解析 | PyMuPDF + python-docx | PDF/Word 全覆盖 |
| 认证 | JWT + bcrypt | 自包含，可对接 SSO |

## 12. 关键决策记录

| # | 决策 | 选择 | 理由 |
|---|------|------|------|
| 1 | 后端语言 | **Node.js/Express** | 已有实现，全栈 TypeScript；50-200 人规模完全胜任 |
| 2 | RAG 服务定位 | **无状态 AI 引擎** | 不感知用户，可嵌入任意系统 |
| 3 | 权限放哪 | **API 网关层** | 认证点单一，RAG 无状态，审计清晰 |
| 4 | 向量数据库 | **ChromaDB** | 轻量免运维，适合 MVP；后期可迁 pgvector |
| 5 | LLM | **DeepSeek → 公司内部模型** | 当前 DeepSeek 验证，协议 OpenAI 兼容可无缝切换 |
| 6 | RAG 框架 | **自建管道** | 灵活可控，避免 LangChain 抽象层开销 |
| 7 | 流式 | **SSE 流式** | 首字延迟低，用户体验好 |
| 8 | .x_t 全文切片 | **第一版不做** | 用户提问场景与坐标数据不匹配 |
| 9 | 对话记录 | **存 API 网关层** | 需关联 user_id，审计追溯 |
| 10 | 数据库 | **SQLite（→ PG 可选）** | 当前零运维，迁 PG 是改一行连接串的事 |

## 13. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| LLM 接口不稳定 | 搜索不可用 | 降级：LLM 失败时展示传统搜索结果 + 错误提示 |
| Embedding 模型下载困难 | 无法向量化 | fallback 模式：纯 Python MD5 hash 替代 |
| 文档解析质量差 | 检索精度下降 | 优先支持文本型 PDF；后叠加 OCR 处理扫描件 |
| 向量检索不准确 | 用户失去信任 | 展示引用来源可验证；后续引入 Re-rank |
| 大量文件并发处理 | 内存/CPU 压力 | 异步任务队列 + 限流 + 进度反馈 |
| 单点故障（SQLite 文件损坏） | 数据丢失 | 定期备份 `data/` 目录；长期迁 PG |
| ChromaDB 数据损坏 | 向量丢失 | 支持 reindex 一键重建 |
