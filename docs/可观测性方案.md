# 可观测性方案

## 当前选型

当前阶段采用 **自研 JSON pull 指标端点**：

- API 暴露 `GET /api/admin/metrics`
- 仅 `system_admin` 可访问
- 进程内维护 5 分钟滚动窗口
- 输出 JSON，方便前端治理页、脚本巡检和未来 Prometheus exporter 复用

暂不直接接入 Prometheus + Grafana。原因是当前项目仍是单机 / 小团队形态，直接上完整指标栈会增加部署、鉴权和上下文成本。等出现长期后台服务、多人运维或线上告警需求后，再把现有 JSON 指标转换为 Prometheus pull。

## 指标口径

`/api/admin/metrics` 当前输出：

- `qps`：滚动窗口请求数 / 窗口秒数
- `latency_ms.p50` / `latency_ms.p95`：API 请求耗时分位数
- `error_rate`：`5xx` 或带 `error_code` 的请求占比
- `llm_call_count`：聊天链路中实际触发 LLM 的次数
- `retrieval_hit_rate`：聊天链路返回引用来源的比例
- `artifact_success_rate`：artifact 相关接口成功率

## 日志口径

API 与 RAG 均输出结构化请求字段：

- `requestId` / `request_id`
- `userId`
- `route`
- `method`
- `duration_ms`
- `status`
- `error_code`

跨服务请求必须通过 `X-Request-Id` 串联。API 接收外部请求时生成或透传 `X-Request-Id`，调用 RAG 时继续传递同一个 requestId。

## 采集边界

当前指标只做轻量运行态观测，不作为审计账本：

- 指标窗口随 API 进程重启清空
- 不记录用户问题正文、文档原文、chunk 内容
- 不在指标里写敏感字段
- 高风险操作仍然写 `audit_logs`

## 后续升级路径

1. 保持 `/api/admin/metrics` JSON 口径稳定。
2. 增加 `/metrics` Prometheus exporter，只做字段映射，不改业务采集点。
3. Grafana 仪表盘从 Prometheus 读取 QPS、P95、错误率、检索命中率和 artifact 成功率。
4. 告警规则只覆盖核心链路：API 5xx、RAG 5xx、P95 超阈值、检索命中率异常下降。

## 验收方式

- `pnpm run build:api`
- `GET /api/admin/metrics` 使用 `system_admin` 返回 200
- 非 `system_admin` 访问返回 403
- 返回体包含 QPS、P50/P95、错误率、LLM 调用次数、检索命中率和 artifact 成功率
