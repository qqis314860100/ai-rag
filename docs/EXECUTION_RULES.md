# 项目执行规则清单

> 这份清单是本项目的默认工作流程。目标不是“代码改完”，而是“功能真的跑通后再提交”。

## 1. 任务完成标准

- 任务必须以“用户可见流程已验证”为结束条件。
- 修 bug 不是只修代码，而是要先复现、再修复、再回归验证。
- 新功能不是只通过编译，而是要把关键路径真实走一遍。
- 任何不确定的行为，都要用实际页面、API 请求或服务健康检查确认。

## 2. 每次动手前先确认

- 这次修改只影响哪个服务：`web` / `api` / `rag`
- 这次要解决的是新功能、bug、还是重构
- 需要验证的真实场景是什么
- 是否会影响登录、聊天、文档、搜索、权限、草稿、滚动、上传、流式响应等核心流程

## 3. 标准执行流程

1. 先读清楚需求或复现问题。
2. 只改必要的地方，保持修改面最小。
3. 改完后先做本地自检，确认没有明显逻辑问题。
4. 再跑对应服务的构建/测试。
5. 再用真实流程验证一次。
6. 只有确认“真的好了”，才允许 commit。

## 4. 不同类型任务的验证要求

### 前端 `web`

- 至少跑 `pnpm build:web`
- 涉及页面、交互、路由、状态、滚动、草稿、流式展示时，必须用浏览器实际走一遍
- 重点检查刷新、切页返回、切换会话、长列表、边界输入、空状态、错误态
- 如果有自动化脚本或 Playwright，可以优先用它复现和回归

### 后端 `api`

- 至少跑 `pnpm build:api`
- 涉及接口、权限、上传、会话、搜索、聊天时，要跑对应的接口烟雾测试
- 优先使用 `api/tests/run-tests.sh` 或相关单测/集成测试脚本
- 变更接口后，至少用 `curl` 或现有脚本确认请求和返回都符合预期

### `rag`

- 至少确认 Python 服务可以启动，并通过健康检查
- 涉及 ingest / search / chat / prompt / embedding 时，要跑对应的烟雾验证
- 优先用现有脚本或 `pytest`，如果没有覆盖，至少做 `python -m compileall` 或等价检查
- 改完后要确认返回内容、引用、过滤条件、异常处理都符合预期

## 5. 提交门槛

- 只有在相关流程验证通过后，才可以 `git commit`
- 仅通过编译不算完成
- 仅看到页面打开不算完成
- 仅日志不报错也不算完成
- 必须是“功能真的能用”

## 6. Commit 规则

- 一个 commit 只改一个服务：`api/`、`web/`、`rag/` 三者不能混在一起
- 使用 Conventional Commits
- `scope` 只允许 `api`、`web`、`rag`
- commit 信息里不要带 AI 相关内容，例如 `Co-Authored-By`、`Claude`、`AI generated`
- 如果一个任务横跨多个服务，拆成多个 commit，分别验证

## 7. 推荐的验收顺序

- 先做最小修改
- 先确认本地能跑
- 再验证真实流程
- 最后整理 commit

## 8. 常用命令

```bash
pnpm build:web
pnpm build:api
cd api && ./tests/run-tests.sh
```
