# 项目执行规则清单

> 这份清单是本项目的默认工作流程。目标是用足够的验证保护质量，同时避免让小改动被流程成本拖慢。

## 1. 任务完成标准

- 任务完成标准按风险分级，不要求所有小功能都反复跑完整链路。
- 修 bug 要有能证明问题被修掉的最小回归；能轻量复现就轻量复现，涉及核心链路再扩展验证。
- 新功能至少要验证改动点本身；只有影响登录、聊天、上传、检索、权限、流式响应等核心路径时，才要求真实流程验证。
- 不确定、跨边界或高风险行为要用实际页面、API 请求或服务健康检查确认。

## 1.1 验证分级

### A 级：轻量验证

适用：文案、样式微调、局部组件状态、类型收口、无外部副作用的小工具函数。

- 跑最小相关检查，例如 `tsc`、单个测试、`python -m compileall`、脚本语法检查，或直接执行目标函数烟雾。
- 不要求浏览器完整回归，不要求全量 build。
- 在最终回复里说明验证范围即可。

### B 级：常规验证

适用：一个服务内的普通功能、接口字段、组件交互、局部数据流。

- 跑服务级最小构建或测试。
- 对用户可见交互做一次定点烟雾，不扩大到无关流程。
- API/RAG 改动优先用现有 smoke 或直接请求验证关键返回。

### C 级：核心链路验证

适用：登录、聊天主流程、流式生成、中断/重试、上传/索引、权限、跨服务契约、数据删除、迁移、自动循环脚本。

- 跑相关服务构建或测试。
- 真实走一遍关键路径。
- 若改动跨服务，分服务提交并分别验证。

## 2. 每次动手前先确认

- 这次修改只影响哪个服务：`web` / `api` / `rag`
- 这次要解决的是新功能、bug、还是重构
- 需要验证的真实场景是什么
- 是否会影响登录、聊天、文档、搜索、权限、草稿、滚动、上传、流式响应等核心流程

## 3. 标准执行流程

1. 先读清楚需求或复现问题。
2. 只改必要的地方，保持修改面最小。
3. 选择 A/B/C 验证等级。
4. 改完后先做本地自检，确认没有明显逻辑问题。
5. 跑该等级所需的最小验证。
6. 只有验证结果覆盖了本次风险，才允许 commit。

## 4. 不同类型任务的验证要求

### 前端 `web`

- A 级：可只跑相关类型检查、单点脚本或组件级烟雾。
- B 级：跑 `pnpm build:web` 或更小的等价检查；涉及页面交互时用浏览器定点走一遍。
- C 级：聊天、路由、滚动、草稿、流式展示等核心路径必须用浏览器真实验证。
- 浏览器验证只覆盖本次风险点，不默认扩展到全量回归。
- 如果有自动化脚本或 Playwright，可以优先用它复现和回归

### 后端 `api`

- A 级：可只跑相关 TypeScript 编译、脚本语法检查或目标函数烟雾。
- B 级：跑 `pnpm build:api` 或相关接口 smoke。
- C 级：权限、上传、会话、搜索、聊天、删除等核心行为要跑对应接口烟雾或集成测试。
- 优先使用具体测试脚本，不默认跑全量 `api/tests/run-tests.sh`。

### `rag`

- A 级：可只跑 `python -m compileall rag/app` 或直接执行目标函数断言。
- B 级：涉及检索结果、prompt、schema 时，补定点 Python smoke 或请求级 smoke。
- C 级：ingest / search / chat / embedding / 服务启动链路要确认服务可启动并通过健康检查。
- 没有 `pytest` 时允许用直接 Python 断言替代，不为安装测试框架消耗任务时间。

## 5. 提交门槛

- 只有在对应验证等级通过后，才可以 `git commit`。
- A 级任务通过最小检查即可提交。
- B 级任务要证明改动点可用。
- C 级任务必须证明关键用户或服务链路可用。

## 6. Commit 规则

- 一个 commit 只改一个服务：`api/`、`web/`、`rag/` 三者不能混在一起
- 如果一个任务横跨多个服务，必须拆成多个 commit，分别完成各自验证后再提交
- 如果当前 diff 已经混入多个服务，先拆分再提交，禁止先混合提交后补救
- 使用 Conventional Commits：`type(scope): description`
- `scope` 只允许 `api`、`web`、`rag`
- commit 信息里不要带 AI 相关内容，例如 `Co-Authored-By`、`Claude`、`AI generated`
- Ralph 自动循环中，功能提交可以顺带只修改 `PRD.md` 的任务 checkbox，用于推进队列；不要为了每个小任务单独提交 `progress.txt`。
- `progress.txt` 只在阶段完成、阻塞、范围变化、用户要求同步、AFK loop 结束时提交。

### 6.1 回滚约束

- 只允许直接回滚单服务 commit
- 混合多个服务的 commit 视为违规提交，不作为长期回滚单位
- 如果历史上出现了混合 commit，优先拆分或重写历史，再做回滚
- 需要回滚时，优先按单个 service commit 处理，避免把无关改动一起撤掉

### 6.2 文档命名约束

- 仅约束新建的人类阅读型文档，例如需求、设计、架构、技术说明、计划、复盘
- 这类文档的新文件名和标题都应使用中文
- 现有历史英文文档名可保留，不要求一次性重命名
- 不影响代码、配置、脚本、测试、资源文件、迁移文件和接口/标识符命名
- 如果新增的是索引/入口型文档，也优先使用中文命名
- 仅在用户明确要求时，才考虑重命名既有文档

### 6.3 自动循环护栏

- Ralph loop 或其他自动循环只允许在清楚的 PRD / progress 约束下运行。
- 每轮只能做一个任务，只能覆盖一个服务，验证等级按 A/B/C 选择。
- AFK 运行前必须确认工作区干净；如果不干净，先处理当前改动或明确获得用户授权。
- 验证失败时立刻停，不要靠下一轮“顺手修掉”来掩盖问题。
- 自动循环不再强制每轮更新 `progress.txt`；状态记录以 PRD checkbox 和 commit message 为主。
- `progress.txt` 作为阶段总结，不作为每个小功能的流水账。

## 7. 推荐的验收顺序

- 先做最小修改
- 先确认本地能跑
- 再验证真实流程
- 最后整理 commit

## 8. 常用命令

```bash
pnpm build:web
pnpm build:api
pnpm run lint
pnpm run verify
pnpm run audit:harness
cd api && ./tests/run-tests.sh
```
