# 项目执行规则清单

> 这份清单是本项目的默认工作流程。目标是用足够的验证保护质量，同时避免让小改动被流程成本拖慢。

## 0. 最佳标准

本项目采用个人/小团队优先的轻量标准：

- 日常开发轻：单主题 commit、最小验证、不维护流水账。
- 架构边界硬：`web` 只做 UI 和客户端状态，`api` 负责业务与权限，`rag` 负责检索、embedding、prompt 和 LLM。
- 高风险才重：登录、聊天主链路、流式、中断/重试、上传/索引、权限、删除、迁移、RAG ingest/search/chat、AFK/Ralph 脚本必须做真实链路或等价验证。
- AFK 单独管：只有 Ralph/AFK 自动循环需要队列、干净工作区、失败停止和阶段性状态记录。

本文件是详细执行规则的唯一细则来源。`AGENTS.md`、`CLAUDE.md`、`README.md` 和其他文档只做入口摘要；如果仓库文档之间出现冲突，以本文件为准。

### 0.1 提交前五问

每次提交前只需要回答这五个问题，答案不清楚就先拆小或补最小验证：

| 问题 | 可提交答案 | 需要停下来的答案 |
|------|------------|------------------|
| 这次只有一个主题吗？ | 能用一句话说明一个用户意图、一个修复或一个流程调整 | 同时包含多个互不因果的功能、修复、样式、文档或重构 |
| 是否跨服务？ | 不跨服务，或跨服务但服务同一个契约/链路 | 只是顺手同时改了多个服务 |
| 是否命中高风险？ | 没碰核心路径，普通改动 | 登录、聊天、流式、上传、检索、权限、删除、迁移、RAG、AFK/发布 |
| 最小验证是什么？ | 能覆盖本次风险的一个具体命令或 smoke | 只说“应该没问题”，没有验证证据 |
| commit 怎么命名？ | `type(scope): 中文描述`，scope 与 diff 范围一致 | scope 和 diff 不匹配，或描述混了多个主题 |

### 0.2 单主题判定

单主题不是“只能改一个服务”，而是“只能表达一个可回滚的意图”。

| 判定 | 标准 |
|------|------|
| 同主题 | 同一用户意图、同一接口契约、同一条用户/服务链路、同一项流程规则，改动之间有直接因果关系 |
| 不同主题 | 只是碰巧一起改、没有调用/契约/流程因果、属于顺手优化、同时修多个无关问题 |
| 不确定 | 默认拆开；不要为了省一次 commit 把主题硬并在一起 |

正例：

- `api` 改聊天接口字段，`web` 同步调用方展示，属于同一接口契约。
- `rag` 调整 search 返回结构，`api` 服务客户端同步解析，属于同一服务链路。
- `docs/EXECUTION_RULES.md` 和 `scripts/audit_diff.py` 同步更新同一条提交规则，属于同一流程规则。

反例：

- 修聊天重试的同时顺手改首页样式，不是同一主题。
- 调整 `rag` 检索参数的同时改 `api` 登录错误文案，不是同一主题。
- 文档补说明时顺手格式化大量无关文件，不是同一主题。

## 1. 任务完成标准

- 任务完成标准只分普通改动和高风险改动，不要求所有小功能都反复跑完整链路。
- 修 bug 要有能证明问题被修掉的最小回归；能轻量复现就轻量复现，涉及核心链路再扩展验证。
- 新功能至少要验证改动点本身；只有影响登录、聊天、上传、检索、权限、流式响应等核心路径时，才要求真实流程验证。
- 不确定、跨边界或高风险行为要用实际页面、API 请求或服务健康检查确认。

## 1.1 验证分档

| 变更类型 | 风险 | 最小验证 | 是否必须真实链路 |
|----------|------|----------|------------------|
| 文案、样式、局部视觉状态 | 普通 | 相关 lint/build、定点浏览器 smoke 或人工检查 | 否 |
| 类型收口、小工具函数、局部数据流 | 普通 | 类型检查、目标函数断言、单个测试或相关 build | 否 |
| 普通接口字段、非核心交互 | 普通 | 服务级 build、接口 smoke 或定点页面 smoke | 否，除非影响核心路径 |
| 登录、会话、权限、删除 | 高风险 | 相关服务 build/test + 真实 API 或页面链路 | 是 |
| 聊天主链路、流式、中断、重试、滚动、草稿 | 高风险 | `web`/`api` 相关验证 + 浏览器真实链路 | 是 |
| 上传、索引、检索、RAG ingest/search/chat、embedding、prompt/LLM | 高风险 | `rag` 语法/服务检查 + 请求级或端到端 smoke | 是 |
| 数据迁移、schema、持久化兼容 | 高风险 | 迁移/回滚或等价数据 smoke | 是 |
| AFK/Ralph、发布、CI、密钥/环境配置 | 高风险 | 脚本语法 + dry run/等价 smoke + 明确失败停止点 | 是 |

普通改动只跑能覆盖改动点的最小检查，不要求完整浏览器回归，不要求全量 `verify`。高风险改动必须证明关键用户或服务链路可用。

## 1.2 上下文预算

- 读文件优先用 `rg` 定位，再用 `sed -n` 读取小范围；不要为了找一个点整份 `cat` 大文件。
- 不把长日志、完整测试输出、浏览器 console 全量内容贴进对话；只截取失败附近或关键证据并总结。
- 不主动读取生成物、构建产物、数据库、PDF、`.playwright-mcp/`、`output/`、`node_modules/`、`dist/` 等大文件，除非任务明确需要。
- 浏览器回归只用于高风险路径；普通 UI 或文档改动使用定点 smoke 或静态检查。
- AFK/Ralph 每轮只传当前任务、队列预览和 `progress.txt` 摘要，不整份注入长期 PRD 或完整历史进度。
- `progress.txt` 只保留阶段摘要、阻塞和 AFK 结束信息；详细历史通过 git commit 追溯。

## 2. 每次动手前先确认

- 这次修改的单一主题是什么
- 是否需要跨 `web` / `api` / `rag`，以及跨服务是否属于同一主题
- 这次要解决的是新功能、bug、还是重构
- 需要验证的最小场景是什么
- 是否会影响登录、聊天、文档、搜索、权限、草稿、滚动、上传、流式响应等核心流程
- 可以先跑 `pnpm run audit:diff` 获得决策卡；脚本只提示，不替代判断

## 3. 标准执行流程

1. 先读清楚需求或复现问题。
2. 只改必要的地方，保持修改面最小。
3. 判断是普通改动还是高风险改动。
4. 改完后先做本地自检，确认没有明显逻辑问题。
5. 可运行 `pnpm run audit:diff` 看变更区域、风险提示和建议验证；这是建议型护栏，不阻塞提交。
6. 跑该风险所需的最小验证。
7. 只有验证结果覆盖了本次风险，才允许 commit。

## 4. 不同类型任务的验证要求

### 前端 `web`

- 普通改动：可只跑相关类型检查、单点脚本、组件级烟雾或 `pnpm build:web`。
- 高风险改动：聊天、路由、滚动、草稿、流式展示等核心路径必须用浏览器真实验证。
- 浏览器验证只覆盖本次风险点，不默认扩展到全量回归。
- 如果有自动化脚本或 Playwright，可以优先用它复现和回归。

### 后端 `api`

- 普通改动：可只跑相关 TypeScript 编译、脚本语法检查、目标函数烟雾、`pnpm build:api` 或相关接口 smoke。
- 高风险改动：权限、上传、会话、搜索、聊天、删除等核心行为要跑对应接口烟雾或集成测试。
- 优先使用具体测试脚本，不默认跑全量 `api/tests/run-tests.sh`。

### `rag`

- 普通改动：可只跑 `python -m compileall rag/app`、目标函数断言、定点 Python smoke 或请求级 smoke。
- 高风险改动：ingest / search / chat / embedding / 服务启动链路要确认服务可启动并通过健康检查。
- 没有 `pytest` 时允许用直接 Python 断言替代，不为安装测试框架消耗任务时间。

## 5. 提交门槛

- 只有在对应验证通过后，才可以 `git commit`。
- 普通改动通过最小检查即可提交。
- 高风险改动必须证明关键用户或服务链路可用。
- 提交前建议跑 `pnpm run audit:diff`，用来辅助判断单主题、风险分档和验证力度；脚本只提醒，不替代人工判断。
- `audit:diff` 如果提示“疑似混主题”，先拆分或在提交说明里能明确证明同主题；不能证明就拆。

### 5.1 严格模式

日常开发默认不启用严格模式。只有 AFK、发布、高风险提交，或用户明确要求时，才使用：

```bash
pnpm run audit:diff -- --strict
```

严格模式只检查四类最容易出事的情况：

| 检查 | 触发 | 通过方式 |
|------|------|----------|
| 高风险改动缺少验证说明 | 命中登录、聊天、上传、检索、权限、删除、迁移、RAG、AFK/发布等风险词 | 先完成验证，再传 `--validation "<命令或证据>"` |
| 跨服务但缺少同主题说明 | 同时改 `web` / `api` / `rag` 中多个服务 | 传 `--topic "<同一用户意图/接口契约/服务链路>"`，或拆分提交 |
| 规则/脚本改动缺少 harness 自检 | 改 `AGENTS.md`、`CLAUDE.md`、执行规则、贡献规则、审计脚本或 `scripts/` | 跑 `pnpm run audit:harness` 后传 `--harness-checked` |
| 明显跨区域但缺少共同主题 | 同时改服务、docs、scripts、repo、other 等多个区域 | 传 `--topic "<共同主题>"`；说不清就拆 |

示例：

```bash
pnpm run audit:diff -- --strict \
  --topic "聊天接口契约和前端展示同步" \
  --validation "pnpm run build:web" \
  --validation "浏览器 smoke：发送消息和重试正常"

pnpm run audit:diff -- --strict \
  --topic "项目规则和 diff 审计同步收敛" \
  --harness-checked
```

## 6. Commit 规则

- 一个 commit 只表达一个主题：一个功能、一个修复、一个重构，或一个流程/文档调整。
- 同主题允许跨服务；必须能说清楚共同的用户意图、接口契约、服务链路或流程规则。
- 无关改动必须拆；无法证明同主题就拆，不要硬并。
- 禁止把无关功能、修复、文档、格式化或多服务杂项混在一个 commit。
- 如果当前 diff 已经混入无关主题，先拆分再提交，禁止先混合提交后补救。
- 使用 Conventional Commits：`type(scope): description`
- 单服务改动优先使用 `api`、`web`、`rag` scope；跨服务或仓库级改动可用 `repo` 或省略 scope
- commit 信息里不要带 AI 相关内容，例如 `Co-Authored-By`、`Claude`、`AI generated`
- Ralph 自动循环中，功能提交可以顺带只修改 `PRD.md` 的任务 checkbox，用于推进队列；不要为了每个小任务单独提交 `progress.txt`。
- `progress.txt` 只在阶段完成、阻塞、范围变化、用户要求同步、AFK loop 结束时提交。

### 6.1 回滚约束

- 直接回滚的单位是单主题 commit
- 混合无关主题的 commit 视为违规提交，不作为长期回滚单位
- 如果历史上出现了无关混杂 commit，优先拆分或重写历史，再做回滚
- 需要回滚时，优先按单个主题处理，避免把无关改动一起撤掉

### 6.2 文档命名约束

- 仅约束新建的人类阅读型文档，例如需求、设计、架构、技术说明、计划、复盘
- 这类文档的新文件名和标题都应使用中文
- 现有历史英文文档名可保留，不要求一次性重命名
- 不影响代码、配置、脚本、测试、资源文件、迁移文件和接口/标识符命名
- 如果新增的是索引/入口型文档，也优先使用中文命名
- 仅在用户明确要求时，才考虑重命名既有文档

### 6.3 自动循环护栏

- Ralph loop 或其他自动循环只允许在清楚的 PRD / progress 约束下运行。
- 每轮只能做队列中的第一个任务；允许同一任务少量跨服务，但不能混入无关主题。
- 验证按普通/高风险两档选择，默认用最小相关检查。
- AFK 运行前必须确认工作区干净；如果不干净，先处理当前改动或明确获得用户授权。
- 验证失败时立刻停，不要靠下一轮“顺手修掉”来掩盖问题。
- 自动循环不再强制每轮更新 `progress.txt`；状态记录以 PRD checkbox 和 commit message 为主。
- `progress.txt` 作为阶段总结，不作为每个小功能的流水账。
- 自动循环提示词不得注入整份 PRD 或完整日志；需要更新 checkbox 时，用当前任务文本在 `PRD.md` 中定位对应行。

## 7. 推荐的验收顺序

- 先做最小修改
- 先确认本地能跑
- 高风险改动再验证真实流程
- 最后整理 commit

## 8. 常用命令

```bash
pnpm build:web
pnpm build:api
pnpm run lint
pnpm run verify
pnpm run audit:harness
pnpm run audit:diff
cd api && ./tests/run-tests.sh
```
