开场先把定位讲清楚：这不是一个聊天工具，也不是为了替代现有 Agent。它是把企业已有文档里的知识真正变成平台能力。
01 / 当前痛点

EP 平台的问题不是不能管文件，而是不能直接用知识

传统文件平台能“找到文件”，但很难“回答问题”。

只搜元数据

  • 文件名、标签、分类、筛选项有效
  • PDF / Word 正文里的内容难以被理解

查找链路长

  • 用户搜索后还要打开文件、翻页、判断
  • 异常处理和参数确认依赖人工经验

知识难沉淀

  • 工程师答过的问题散落在口头、群聊和会议里
  • 缺少 FAQ、知识卡、版本和审核机制
痛点不是“文件没地方放”，而是“文件里的知识没有被可靠地使用”。
EP 管文件，RAG 负责可信回答，LLM Wiki 负责长期沉淀。
这一页不要否定 EP。EP 的文件管理、权限、存储仍然重要。我们要补的是内容级检索、带证据回答和知识治理。
02 / 建设原因

为什么要做这样一个平台

企业产线需要的是可信知识工作台，不是通用聊天窗口。

业务问题天然是知识问题

  • 某个 SOP 怎么执行？
  • 某个参数范围是多少？
  • 某个报警怎么排查？
  • 不同版本规范差异在哪里？

企业回答必须可验证

  • 回答要有引用来源
  • 证据不足要拒答或提示
  • 文档冲突要暴露风险
  • 权限、审计、版本要可追溯
目标是从“文件管理”升级到“知识使用”：问问题 → 查证据 → 得答案 → 沉淀资产。
RAG 知识库的核心价值在可信链路，而不是生成一段漂亮文字。
这里强调企业场景的特殊性。普通 AI 回答看起来合理还不够，产线、质量、安全场景必须知道依据在哪里。
03 / 系统定位

这个系统到底是干嘛的

它做三件事：RAG 让知识可问，LLM Wiki 让知识可沉淀。

1. 文档变知识库

解析 PDF、Word、Markdown、SOP 和设备手册，切分、向量化、建立语义检索能力。

2. 回答变可信输出

回答绑定引用、片段、claim、confidence；低信息、无引用、低证据时不强行回答。

3. 问答变知识资产

高价值回答沉淀为知识卡、FAQ、术语库、流程图和关系网络，经人工审核后复用。

04 / 使用场景

典型用户和问题

围绕产线、工艺、质量、设备、安全的高频知识场景。

角色 典型问题 系统输出
产线操作员 模组 EOL 测试前需要确认哪些步骤？ 步骤化回答、SOP 引用、流程图
工艺工程师 Busbar 激光焊接关键参数范围是什么？ 参数表、版本信息、来源片段

知识管理员 哪些问题经常拒答？哪些文档需要补充？ 知识缺口、低质量文档、待审核资产
最终体验：用户在业务页面内直接提问，答案能回到原文和业务对象。
这些场景都不是“写代码”或“让 Agent 帮忙总结”。它们是普通业务用户每天会遇到的知识使用问题。
05 / 平台价值

价值在哪里

减少查找成本，降低误用风险，沉淀组织知识。

快

查得更快

从人工翻文档变成自然语言检索和定位。

准

答得更准

回答必须带引用，能回到原文确认。

稳

风险更可控

低证据拒答，冲突提示，不把猜测包装成结论。

沉

知识可沉淀

高价值回答进入 FAQ、知识卡和术语库。

最终不是让某个会 AI 的人更强，而是让整个组织都能稳定使用可信知识。
价值评估可看：引用打开率、采纳率、误拒率、知识卡发布率。
这一页可以用来回答管理层最关心的问题：这个东西不是炫技，而是降低查找、判断、培训和知识流失成本。
06 / 与 Opencode / Agent 的区别

公司内部已有 Agent，为什么还需要这个系统

Opencode 是个人工作台；RAG + LLM Wiki 是企业知识基础设施。

维度 Opencode / Agent + Skill RAG + LLM Wiki 知识平台
使用对象 开发者、AI 熟练用户 产线、工艺、质量、设备、安全、管理人员
使用方式 会写 prompt、会操作 Agent 在业务页面内直接提问
知识来源 临时读文件或指定上下文 企业文档统一解析、索引、权限过滤
可信机制 可做，但依赖使用者约束 引用、claim、置信度、拒答、审计标准化
知识治理 偏一次性任务和个人效率 FAQ、知识卡、术语、审核、版本、归档
业务嵌入 不适合直接嵌入 MES / EP / 天枢页面 可作为平台能力嵌入业务系统
二者不是替代关系：Agent 做个人增强，RAG 知识库做组织级服务。
这一页是核心。不要说 Opencode 不好，它非常适合开发者和自动化。但企业知识库要面向普通业务用户、权限、审计、长期治理。
07 / RAG 与 LLM Wiki

不是二选一，而是两层能力

RAG 解决“基于文档怎么答”，LLM Wiki 解决“优质答案怎么沉淀”。

RAG 层：即时可信问答

  • 用户提问后检索相关文档片段
  • LLM 基于引用证据生成回答
  • 适合长尾问题、临时查询、跨文档查找

LLM Wiki 层：长期知识资产

  • 高置信回答沉淀为知识卡、FAQ、术语和主题页
  • 人工审核、版本管理、反向引用和失效标记
  • 适合高频问题、培训内容、标准流程和组织复用

08 / 与公司平台的关系

不是另起炉灶，而是先做产线 AI 知识能力孵化层

公司知识库和在线 Agent 平台是最终承载方；当前项目负责把产线闭环先跑通。

公司知识库

擅长文档归档、分类、权限和检索；但不一定天然具备产线级可信问答、引用片段、误拒治理和知识沉淀闭环。

在线 Agent 平台

擅长通用对话、工具调用和智能体编排；但产线还需要文档版本、客户隔离、工艺语境、审计和 MES 场景嵌入。

当前项目

作为轻量试验田，先验证 RAG + LLM Wiki 闭环：可信回答、知识卡/FAQ、质量反馈、权限过滤和业务接入方式。

09 / 赋能产线闭环

怎么真正进入产线，而不是停留在演示问答

把“查资料、问专家、改文档、复盘问题”变成一条可治理闭环。

权限控制

按用户、角色、产线、工艺、客户资料和安全等级控制可见范围。

统一知识源

员工不再各自维护一份过期资料，统一从受控文档和已发布知识资产取数。

引用可追溯

回答必须定位到文档、章节、页码、chunk 或片段，方便现场复核。

协作沉淀

好回答可以沉淀为知识卡、FAQ、SOP 片段、流程图，经审核后复用。

质量闭环

错答、拒答、低置信和高频失败问题进入治理队列，反向驱动补文档和调检索。

审计合规

谁问了什么、用了哪些资料、生成了什么结论、是否被采纳都可追踪。

企业语境

越用越懂公司术语、设备别名、产线结构、客户代号和文档组织方式。

业务集成

可接入 MES、工位看板、工单和 EP/天枢页面，在业务现场直接触发问答。

产线闭环的关键：把 AI 输出纳入权限、证据、协作、审计和治理，而不是让它自由发挥。
这一页要讲“闭环”。现场人员提问后，系统先按权限过滤资料，再基于证据回答；用户反馈会进入治理队列；高价值回答审核后沉淀为知识资产，再反哺下一次检索。MES 等业务系统接入后，问答发生在业务现场，而不是另开一个孤立聊天工具。
10 / 意义与下一步

项目意义

让 EP / 天枢从“文件入口”升级为“智能知识入口”。

当前阶段

  • RAG 原型链路跑通
  • 具备问答、引用、知识资产雏形
  • 仍需真实数据和平台接入验证

近期建议

  • 选 1 个真实业务入口试点
  • 导入 50-200 份真实文档
  • 建立 30-50 条验收问题

融合方向

  • 对接 SSO、权限和审计
  • 嵌入文档页 / 工单页 / 看板
  • 沉淀 FAQ、知识卡和治理流程
这个系统的意义：把“个人会不会用 AI”变成“组织能不能稳定、安全、可追溯地使用知识”。
建议先做小范围真实试点，再扩大到平台化。
最后收束到下一步：不要一上来做大平台重构。先选一个真实入口，把价值跑出来，再进入正式融合。
