## 1. 产品定位

面向电池产线工艺、设备、质量、SOP、MES、维护、安全的可追溯智能问答与知识沉淀系统。

主流程：

```
问 → 检索 → 带证据回答 → 自动出图/出表 → 沉淀为知识资产 → 反哺检索
```

非目标：

- 不是通用搜索引擎
- 不是 Wiki 编辑器（虽然吸收了 Wiki 的人审与术语层）
- 不是学习/课程产品（学习只是其中一个使用场景）

## 2. 服务拓扑

```
┌────────────────────┐    HTTP/SSE    ┌──────────────────────┐    HTTP    ┌──────────────────────┐
│  web  (Vite :5174) │ ──────────────▶│  api  (Express :3001)│ ──────────▶│  rag  (FastAPI :8000)│
│  React 19 + TS     │                │  Node 20 + SQLite    │            │  Python 3.11 + Chroma│
└────────────────────┘                └──────────┬───────────┘            └──────────┬───────────┘
                                                 │                                   │
                                                 ▼                                   ▼
                                          data/ai-rag.db                       data/chroma/
                                          data/uploads/                        knowledge/  (源文档)
```

| 服务 | 端口 | 启动 | 主要职责 |
|------|------|------|----------|
| `web` | 5174 | `pnpm dev:web` | 页面、交互、路由、视觉状态、客户端缓存 |
| `api` | 3001 | `pnpm dev:api` | 认证、会话、消息、文档、artifact、笔记、知识资产、权限、审计 |
| `rag` | 8000 | `pnpm dev:rag` | 解析、切分、embedding、检索、prompt、LLM、Diagram IR、Visual Planner、知识图谱 |

硬边界：

- `web` 不直连数据库、不直连 `rag`
- `api` 通过 `services/ragClient.ts` 走 HTTP 调用 `rag`，不内嵌检索逻辑
- `rag` 不持有用户身份和权限，只接收 `api` 编排后的请求

## 4. 数据模型

`api/src/db/index.ts` 集中建表，按主题分组：

| 主题 | 表 |
|------|-----|
| 身份与权限 | `users`, `roles`, `role_permissions` |
| 文档与切片 | `documents`, `document_versions`, `document_jobs`, `doc_comments` |
| 会话 | `chat_sessions`, `chat_messages`, `message_sources` |
| 用户互动 | `feedback`, `favorites`, `browse_history`, `chat_notes` |
| 产物 | `chat_artifacts` |
| 知识资产 | `terminology_terms`, `knowledge_cards`, `knowledge_card_versions`, `knowledge_faqs` |
| 平台 | `audit_logs`, `settings` |
| 预留 | `agents`, `agent_tools`, `agent_memories` |

约束：

- `chat_artifacts` / `chat_notes` 都按 message/source 维度挂载，便于按回答聚合
- `knowledge_cards` 走 AI 草稿 → 待审核 → 发布 → 归档 的状态机，并有版本历史
- `knowledge_faqs` 与 `knowledge_cards` 在数据上独立，但通过 `knowledgeAssetContextService` 一起反哺到 RAG

## 5. 端到端关键链路

### 5.1 文档导入

```
web 上传 → POST /api/documents
api 落 documents/document_versions/document_jobs，将文件存到 data/uploads
api → POST /rag/documents/ingest
rag 解析(parsers) → 清洗(cleaning) → 切分(chunking) → embedding → 写 Chroma
rag 返回 chunk 元信息 → api 落 message_sources 可索引信息
```

### 5.2 聊天问答（流式）

```
web POST /api/chat (stream=true)
api 创建 user message → 调 ragClient.chat
rag pipeline：
  ① 术语扩展 + 多轮问题重写
  ② 检索 + 重排 + 证据收集
  ③ refusal 判定（低证据/冲突/低信息）
  ④ LLM 流式生成
  ⑤ 输出 AnswerIR (answer + claims + citations + confidence + warnings)
SSE meta → SSE token → SSE done
api 保存 assistant message + sources + AnswerIR 摘要到 metadata
api 异步触发 Visual Planner（diagram/flowchart/mindmap/table）
rag DiagramIR → Excalidraw scene
api 落 chat_artifacts → SSE artifact_ready
web 渲染回答 + 引用 + ArtifactCard
```

### 5.3 知识沉淀回路

```
高置信回答 + 引用 + 笔记 + Diagram artifact
  → knowledgeCardDraftService 生成知识卡草稿（低置信/拒答不生成）
  → 审核人通过 knowledge.ts 路由审批发布
  → knowledgeGovernanceService 暴露治理视图
  → 已发布术语 / 知识卡 / FAQ 由 knowledgeAssetContextService
    在下次 RAG 检索时作为扩展上下文回流
  → 回答 metadata 标记使用了哪些资产，保证可追溯
```

## 6. 现状观察

下面这些不是 bug，但都是已经能看见的架构债。

### 6.1 命名错位：`rag/app/evaluation/` 实际是 artifact 生成

里面 1480 行的 `diagram_ir.py`、`visual_planner.py`、`knowledge_assets.py`、`knowledge_graph.py`、`image_artifact.py` 都是**生产侧**逻辑。真正的质量评估在 `rag/evals/`。任何新人看到 `evaluation/` 都会以为是 eval，会找错地方加代码。

升级方案 [§11.1](企业级文档知识库智能工作台升级方案.md) 里建议的目录其实就是 `rag/app/artifacts/`，应当按这个名字归位。

### 6.2 巨石文件

| 文件 | 行数 | 现状 |
|------|------|------|
| `rag/app/core/pipeline.py` | 899 | 重写、检索、生成、AnswerIR、refusal、术语扩展、流式拼接挤在一起 |
| `rag/app/evaluation/diagram_ir.py` | 1480 | IR schema + 校验 + 生成 + Excalidraw 转换 全在一个文件 |
| `api/src/routes/chat.ts` | 1433 | 23 个 `router.*`，覆盖 chat、sessions、messages、notes、sources、diagram、artifacts |
| `api/src/db/index.ts` | 555 | 16 张表 DDL + 索引 + 默认数据全集中在一文件 |
| `web/src/components/chat/ChatThread.tsx` | ~1.2K | 渲染、流式、艺术品挂载、选择态都在一起 |

巨石本身没错，但已经到了**新增一个能力会很难定位**的程度。

### 6.3 源目录 .js 与 .tsx 同名共存

`web/src` 下 56 个 `.js` 文件 + 56 个 `.tsx` 文件（数量完全相等）。例如 `App.js`、`App.tsx` 并存，`ChatPage.js` / `ChatPage.tsx` 并存。`.js` 看上去是 TS 编译产物被错误地写回了 `src/`，Vite 实际只编 `.tsx`，`.js` 是死代码，但会污染搜索、IDE 跳转和 git diff。

### 6.4 端口和默认值漂移

| 位置 | RAG 端口 |
|------|----------|
| `README.md` | 8001 |
| `rag/app/main.py` 默认值 | （uvicorn CLI 决定） |
| `package.json` `dev:rag` | **8000** |
| `api` `RAG_SERVICE_URL` 默认 | 需要核对 `.env.example` |

不影响运行（实际启动用 package.json），但 README 是错的。

### 6.5 文档与入口分散

根目录散落：

- `README.md`, `AGENTS.md`, `CLAUDE.md`, `PRD.md`, `progress.txt`
- `企业知识库RAG精准问答+多轮会话记忆 全套落地流程方案.md`（根目录，13KB）
- `人类阅读的/`（目录名本身就让人困惑）
  - `windows设置.md` / `产品说明.md` / `团队讨论.md`

`docs/` 下又另有一套。新人完全不知道先读什么。

### 6.6 跨服务的命名不一致

- 前端叫 `artifact`，后端叫 `chat_artifacts`，RAG 叫 `diagram` / `image_artifact` —— 同一概念多套词
- 前端 `ConversationNavigator` 内部叫"知识工作台"，PRD 叫"右侧栏"，方案文档叫"右侧栏 = 路线图 + 知识笔记"

不致命，但跨服务联调时会反复对暗号。

### 6.7 没有"现状架构图"

到这份文档之前，没有任何一份文档画出三服务、数据流、端口、表分组。新接手的人必须从代码里拼。

## 7. 优化建议（按收益/成本排序）

### 优先级 P0 — 1~2 小时能做完，收益立竿见影

1. **重命名 `rag/app/evaluation/` → `rag/app/artifacts/`**。这是单纯的命名错位，重命名 + 改 import 即可，没有行为变化。同时新建 `rag/app/artifacts/README.md` 写清楚和 `rag/evals/` 的区别。
2. **删掉 `web/src/**/*.js`**。先确认 `tsconfig.json` 没有 `outDir: src/`（应该是 `dist/`），然后批量 `find web/src -name "*.js" -delete`，跑 `pnpm build:web` 确认无回归。
3. **修正 `README.md` 的 RAG 端口为 8000**，或反过来把 `package.json` 和 `.env.example` 统一到 8001——选一个口径写死。
4. **把"人类阅读的/"重命名为 `docs/参考资料/`**，把 `企业知识库...落地流程方案.md` 一并移入 `docs/参考资料/`。根目录只保留 README/AGENTS/CLAUDE/PRD/progress。

### 优先级 P1 — 几个迭代里逐步做

5. **拆分 `api/src/routes/chat.ts`**：
   - `routes/chat/sessions.ts`（会话 CRUD）
   - `routes/chat/messages.ts`（消息 CRUD + 编辑 + 删除分支）
   - `routes/chat/notes.ts`（含 contract / aggregate）
   - `routes/chat/sources.ts`（消息引用详情）
   - `routes/chat/artifacts.ts`（diagram / artifact / image contract）
   - `routes/chat/index.ts` 只做装配
   单主题原则下，每次只拆一类，commit 写清"路由结构调整、行为不变"。
6. **拆分 `rag/app/core/pipeline.py`** 按阶段：
   - `pipeline/rewrite.py`
   - `pipeline/retrieve.py`
   - `pipeline/generate.py`
   - `pipeline/refusal.py`
   - `pipeline/__init__.py` 顺序编排
7. **拆分 `api/src/db/index.ts`**：按主题分文件（identity / documents / chat / artifacts / knowledge / platform），`index.ts` 只做 `initDb` 装配。
8. **统一跨服务命名**：所有"artifact / diagram / chart / table / image"统一用 `artifact` + `type` 字段（数据库表名保留 `chat_artifacts`，但 API/前端/RAG 类型字段统一）。

### 优先级 P2 — 演进性收益，不紧急

9. **在 `api/src/services/ragClient.ts` 上加 schema 校验**：RAG 返回的 `AnswerIR` / `DiagramIR` 用 zod 校验，让契约破坏在边界爆出来而不是渗到前端。
10. **抽出 `web/src/features/chat/`** 把 `pages/ChatPage.tsx` + `components/chat/*` + 对应 hooks/types 收敛进一个 feature 目录，其他页面同样。当前所有 `components/*` 是按 UI 类型分类，已经有点撑不住。
11. **画一份运行时拓扑 + 数据流图**（Excalidraw 或 mermaid）放到 `docs/图/`，作为本文档的可视化补充。
12. **CI 上跑 `rag/evals/`**：现在 evals 已经存在，但没有跨服务自动化跑分。可以在 `pnpm run verify` 后增加一条 `rag` 的 eval smoke。

### 不建议现在做的事

- 不要现在引入 monorepo 工具升级（Turborepo / Nx）。当前 pnpm workspace 够用，引入工具反而增加上下文成本。
- 不要现在把 SQLite 换成 Postgres。除非有多人并发写入或部署到多机的明确需求，SQLite 是这种产品形态最经济的选择。
- 不要现在抽公共 `shared/` 包共享类型。先按 5/6/7 拆完巨石和命名再考虑，否则会增加耦合。
