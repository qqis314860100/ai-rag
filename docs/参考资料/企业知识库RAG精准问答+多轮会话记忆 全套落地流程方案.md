# 企业知识库 RAG 精准问答与多轮会话记忆落地方案评审

## 1. 方案结论

这份方案的方向是对的：企业知识库问答要从“普通 RAG 问答”升级为“检索、重写、结构化回答、证据校验、会话记忆、图解渲染”的闭环系统。

但原方案存在一个核心问题：它把“理想效果”写成了“必然效果”。例如“100% 贴合企业文档”“彻底杜绝幻觉”“模型输出 100% 匹配规范”这类表述不适合作为工程方案。生产系统不能依赖口号保证正确性，必须依赖可验证机制：检索质量、引用覆盖、schema 校验、失败兜底、人工可追溯。

结合当前 `ai-rag` 项目现状，最佳落地路径不是一次性重写全链路，而是分三阶段渐进升级：

1. 先补齐精准问答和多轮问题重写。
2. 再把图解生成升级为 LLM structured output + schema 校验。
3. 最后做自动出图判定、长期记忆和质量评估闭环。

## 2. 原方案主要不足

### 2.1 过度承诺，缺少可验证边界

原文多次使用“100%”“彻底杜绝”“完全一致”等表述。企业 RAG 可以降低幻觉，但不能保证绝对无幻觉。

更准确的标准应该是：

- 低证据时拒答或提示信息不足。
- 有效回答必须绑定引用。
- 结构化输出必须通过 schema 校验。
- 置信度只表达证据强弱，不表达事实绝对正确。
- 关键业务场景保留人工核对入口。

### 2.2 没区分模型能力、检索能力和渲染能力

原方案把“回答精准”“图解正确”“前端高保真”混成一个链路描述，但三者问题不同：

- 回答精准取决于召回、重排、prompt、引用约束和拒答策略。
- 图解正确取决于模型是否能提炼结构化 DiagramIR。
- 图表好看取决于布局算法和前端渲染组件。

三层必须解耦，否则容易出现“文本回答还行，但图是关键词堆叠”的问题。

### 2.3 Structured Outputs 说法正确，但未落到当前技术栈

当前项目 README 显示 LLM 层使用 DeepSeek API，RAG 服务是 Python FastAPI，不是 Vercel AI SDK 驱动的 Node 全栈结构化生成。因此不能直接按 Vercel AI SDK 的写法落地。

本项目更适合的落地方式是：

- `rag` 侧定义 Pydantic schema。
- LLM 输出 JSON。
- Python 侧做 `json.loads` + Pydantic 校验。
- 校验失败时重试一次或降级为无图回答。
- `api` 只转发标准化结构和持久化。
- `web` 纯渲染。

如果后续切到 OpenAI Structured Outputs，可以再替换模型调用层，不应影响 API 和前端契约。

### 2.4 问答 Schema 太粗，缺少拒答和证据覆盖字段

原方案的 `answer / keySteps / keyParams / citations / confidence / isValid` 有方向，但不够生产化。

建议补充：

- `answer_status`：`answered` / `insufficient_context` / `conflict` / `unsafe`。
- `query_rewrite`：记录本轮是否重写，以及重写后的检索查询。
- `claims`：每个结论单独绑定证据，避免整段答案只挂几个引用。
- `missing_info`：回答不了时告诉用户缺什么信息。
- `citation_coverage`：引用是否覆盖所有关键结论。
- `warnings`：低置信、证据冲突、引用不足、图解降级等。

### 2.5 会话记忆方案偏泛，缺少企业隔离与失效策略

原方案提到 `history` 和长期记忆，但没有说明：

- 用户权限变化后历史引用是否还能访问。
- 文档更新、重建索引后旧引用是否失效。
- 长期记忆如何删除、归档、用户可控。
- 记忆是否影响检索过滤，是否会造成越权召回。
- 什么时候用摘要，什么时候用原始最近轮次。

企业知识库里，记忆不是越多越好。最佳做法是“短期对话上下文 + 可审计摘要 + 用户可控偏好”，不要把所有历史都塞进 prompt。

### 2.6 图解方案仍然把“自动出图”说得过满

自动出图是有价值的，但不能简单写成“满足规则必须出图”。实际应该先判断：

- 用户是否需要图。
- 回答是否有足够结构。
- 引用证据是否支持结构关系。
- 图解是否比文字更清晰。
- 节点和边是否能通过 schema 校验。

若用户输入很乱、回答只是澄清、证据不足，就应该明确不生成图。

### 2.7 前端“只渲染、不修正”不等于不校验

原方案说前端不做业务逻辑是对的，但前端仍需要做渲染安全校验：

- 节点 ID 去重检查。
- 边的 source / target 是否存在。
- 节点数量上限。
- 文本长度截断。
- 布局失败兜底。
- 不可信 artifact 不展示生成按钮。

前端不应该提取业务含义，但必须保护用户体验。

### 2.8 缺少质量评估闭环

精准 RAG 不能只靠 prompt，需要评估集：

- 常见问题集。
- 指代追问集。
- 低信息输入集。
- 权限过滤集。
- 参数问答集。
- 流程图生成集。
- 引用覆盖率检查。

没有评估集，就无法判断“精准度是否真的提升”。

## 3. 修正后的推荐架构

### 3.1 总体链路

```text
用户提问
→ API 保存用户消息
→ API 读取最近对话与会话摘要
→ RAG 执行问题重写
→ RAG 检索 + 关键词重排 + 元数据过滤
→ RAG 构建引用上下文
→ LLM 输出结构化 AnswerIR
→ RAG 校验 AnswerIR 与引用覆盖
→ API 持久化回答、引用和元数据
→ 按需生成 DiagramIR
→ API 校验图解资格和拓扑合法性
→ Web 渲染答案、证据、图解
```

### 3.2 AnswerIR 建议结构

```json
{
  "answer_status": "answered",
  "answer": "精简回答正文",
  "query_rewrite": {
    "needed": true,
    "rewritten_query": "补全指代后的检索问题",
    "reason": "用户使用了上一轮指代"
  },
  "claims": [
    {
      "id": "claim_1",
      "text": "关键结论",
      "type": "step",
      "citation_ids": ["chunk_1"]
    }
  ],
  "key_steps": [],
  "key_params": [],
  "risks": [],
  "missing_info": [],
  "citations": [
    {
      "id": "chunk_1",
      "document_id": "doc_1",
      "document_title": "文档名",
      "section_path": "章节",
      "quote": "原文片段"
    }
  ],
  "confidence": 0.82,
  "warnings": []
}
```

### 3.3 DiagramIR 建议结构

```json
{
  "can_generate": true,
  "diagram_type": "flowchart",
  "title": "图解标题",
  "reason": "回答包含明确步骤和条件分支",
  "nodes": [
    {
      "id": "n1",
      "label": "选择导出流程",
      "kind": "step",
      "summary": "一步内可读的短描述",
      "citation_ids": ["chunk_1"]
    }
  ],
  "edges": [
    {
      "source": "n1",
      "target": "n2",
      "label": "下一步",
      "relation": "sequence"
    }
  ],
  "layout_hint": "top_down",
  "quality": {
    "node_count": 6,
    "edge_count": 5,
    "citation_coverage": 1
  },
  "warnings": []
}
```

### 3.4 关键原则

- LLM 负责语义提炼，不让前端猜业务含义。
- Schema 负责格式约束，不把自由文本直接交给前端。
- API / RAG 负责校验，不合格就拒绝或降级。
- 前端负责纯渲染和体验兜底，不写业务提取规则。
- 低信息输入、澄清型回答、低证据回答不生成图解。

## 4. 当前项目可行性判断

### 4.1 已具备基础

当前项目已经有较好的落地基础：

- `web` / `api` / `rag` 三服务边界清晰。
- API 已有会话、消息、引用、artifact 持久化。
- RAG 已有 query rewrite 的初步函数、关键词重排、confidence 估算。
- 前端已有聊天流、证据查看、artifact 弹窗和 Excalidraw 渲染。
- 已经开始限制低信息输入生成图解。
- 已有 `message_sources`，方便做引用追溯。

因此，这份方案在本项目中是可行的，但不能按原文一次性落地。

### 4.2 主要差距

| 能力 | 当前状态 | 差距 |
|------|----------|------|
| 多轮记忆 | API 传最近历史，RAG prompt 使用最近 6 条 | 缺少独立 query rewrite schema、会话摘要和记忆策略 |
| 精准回答 | 有检索、重排、confidence、引用 | 缺少 AnswerIR、claim 级引用和拒答结构 |
| 结构化输出 | 图解已有 DiagramIR，但主要是规则抽取 | 需要升级为 LLM structured output |
| 图解质量 | 前端可渲染 Excalidraw | 需要后端语义提炼、拓扑校验、布局分层 |
| 自动出图 | 当前由用户点击生成 | 可先保留手动，再做智能推荐，不建议立刻强制自动 |
| 评估闭环 | 有部分 RAG tests | 需要新增问题集和图解质量测试 |

### 4.3 风险判断

整体风险中高，但可控。

最高风险点不是前端渲染，而是：

1. LLM 输出的结构化内容是否被证据支持。
2. 多轮问题重写是否会改写用户真实意图。
3. 自动出图是否把弱结构内容强行画成流程。
4. 置信度是否继续误导用户。

所以必须先做 schema 和校验，再做自动化体验。

## 5. 可执行任务清单

### 阶段一：精准问答与多轮重写

1. 定义 `AnswerIR` Pydantic schema。
   - 服务：`rag`
   - 验收：包含 `answer_status`、`claims`、`citations`、`confidence`、`warnings`。

2. 将现有自由文本回答包装为结构化 AnswerIR。
   - 服务：`rag` / `api`
   - 验收：API 返回仍兼容现有 `answer/sources/confidence/followups`，同时保留结构化元数据。

3. 增强多轮问题重写。
   - 服务：`rag`
   - 验收：指代问题能生成独立检索 query；无歧义问题不改写。

4. 保存 query rewrite 结果到消息 metadata。
   - 服务：`api`
   - 验收：每轮回答可追踪原始问题、重写问题、是否重写。

5. 增加拒答策略。
   - 服务：`rag`
   - 验收：低信息输入、无引用命中、证据不足时返回 `answer_status=insufficient_context`。

### 阶段二：图解生成升级

6. 定义新版 `DiagramIR` schema。
   - 服务：`rag`
   - 验收：支持 `can_generate`、`diagram_type`、`nodes`、`edges`、`layout_hint`、`warnings`。

7. 将图解生成从关键词规则升级为 LLM structured output。
   - 服务：`rag`
   - 验收：输入回答和引用，输出精炼节点；不把证据节点画进图。

8. 增加 DiagramIR 校验器。
   - 服务：`rag` / `api`
   - 验收：拦截重复节点、悬空边、节点过多、无引用节点、低信号图解。

9. 改造 artifact 置信度。
   - 服务：`api`
   - 验收：artifact confidence 不再直接复用回答 confidence，而是使用图解质量分。

10. 前端保持纯渲染。
    - 服务：`web`
    - 验收：前端不再做关键词提取，只校验和渲染后端 DiagramIR。

### 阶段三：智能出图与体验收敛

11. 增加出图推荐判定。
    - 服务：`rag`
    - 验收：返回 `diagram_recommendation`，包含推荐类型和原因；默认不强制自动生成。

12. 前端把“生成图解”改成智能建议入口。
    - 服务：`web`
    - 验收：回答右下角展示“可生成流程图/思维导图”；信息不足时展示原因。

13. 支持历史 artifact 回放。
    - 服务：`api` / `web`
    - 验收：历史图表直接读取持久化 payload，不重新生成。

14. 优化图表布局。
    - 服务：`web`
    - 验收：流程图自上而下，思维导图父子层级清晰，连线不穿节点。

### 阶段四：评估与质量闭环

15. 建立 RAG 精准问答评估集。
    - 服务：`rag`
    - 验收：覆盖参数问答、流程问答、异常排查、无答案拒答。

16. 建立多轮问题重写评估集。
    - 服务：`rag`
    - 验收：覆盖“那怎么处理”“这个参数是多少”等指代追问。

17. 建立图解质量评估集。
    - 服务：`rag` / `web`
    - 验收：检查节点数量、边合法性、引用覆盖、图解可读性。

18. 增加调试面板输出。
    - 服务：`web` / `api`
    - 验收：开发环境可查看重写 query、命中文档、claims、warnings、DiagramIR。

## 6. 推荐实施顺序

优先顺序：

1. 阶段一任务 1-5：先把回答结构化和拒答做好。
2. 阶段二任务 6-10：再升级图解生成。
3. 阶段四任务 15-17：同步补评估集，防止越改越玄学。
4. 阶段三任务 11-14：最后做智能推荐和体验增强。

不建议现在立刻做：

- 全自动强制出图。
- 长期用户偏好记忆。
- 完整替换为 OpenAI / Vercel AI SDK。
- 前端继续增加业务提取规则。

## 7. 本项目落地建议

当前 `ai-rag` 最适合的下一步是：

1. 在 `rag` 内新增结构化输出模块，不直接改掉现有 chat 主链路。
2. 先让非流式 `/rag/chat` 支持 AnswerIR，流式接口后续再兼容。
3. 图解生成优先走“点击生成”，不要立即自动生成。
4. 用 10-20 条真实企业知识库问题做小型评估集。
5. 每完成一阶段都保持旧接口兼容，避免前端和 API 一起大改导致回归困难。

一句话判断：这份方案方向可行，但必须从“理想化全套方案”降级为“分阶段、可验证、可回滚的工程任务”。本项目基础已经足够，下一步关键不是继续写前端规则，而是让 `rag` 输出可校验的结构化 AnswerIR 和 DiagramIR。
